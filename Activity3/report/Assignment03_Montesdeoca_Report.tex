\section{Introduction}
\label{sec:intro}

Matrix multiplication is a fundamental operation in many scientific and
industrial applications such as machine learning, data processing, and
simulations. However, its computational cost grows as $O(n^3)$ for matrices of
size $n \times n$~\cite{golub2013}. The goal of this project is to evaluate
the performance improvement obtained through parallelism in shared memory,
and to answer a practical question: how does the thread count affect the
execution time, and where does the speedup saturate? As an optional
extension, we also measure how much performance the compiler can extract from
the same algorithm through SIMD vectorization.

We implement and compare three approaches:
\begin{itemize}
\item Sequential algorithm (classic i-j-k triple loop in C, \texttt{double}
precision);
\item Parallel execution using OpenMP~\cite{dagum1998,openmp52} (the same
i-j-k kernel, parallelized over the rows of the result matrix);
\item Sequential i-k-j variant (same arithmetic work and storage, only the
loop order changes, so the innermost loop becomes a vectorizable rank-1
row update).
\end{itemize}

\section{Methodology}
\label{sec:method}

Random square matrices of sizes 250, 500, and 1000 were generated using
double-precision floating-point values (a deterministic generator with seed
42; the smaller sizes 10 and 100 were used only for validation). Each
implementation multiplies matrices using the same algorithm, except with
different parallelization strategies, and the same pair of input matrices
$(\mathbf{A}, \mathbf{B})$ is used for every method and thread count of a
given size.

Execution time was measured using \texttt{QueryPerformanceCounter}~\cite{msqpc}
and converted to milliseconds. This API was chosen over
\texttt{omp\_get\_wtime()}, which in libgomp on Windows~\cite{libgomp} only
resolves about 1 ms and would quantize the smaller sizes. Each configuration was measured with 2 warm-up runs (excluded
from the samples) followed by 5 measured repetitions; the reported statistic
is the median of the 5 samples. Only the multiplication kernel is timed;
matrix loading and allocation are outside the timed region.

Correctness was verified before benchmarking: the checksum of the result
matrix is compared against the sequential reference after every parallel
configuration (relative tolerance $10^{-6}$), and the sequential result for
$n=10$ matches NumPy's \texttt{A @ B} with a maximum absolute difference of
$4.9 \times 10^{-7}$. All validations passed.

All experiments were executed on a machine with:
\begin{itemize}
\item CPU: Intel Core Ultra 7 155H (Meteor Lake) --- 6 P-cores + 8 E-cores +
2 low-power E-cores = 16 physical cores / 22 hardware threads, P-cores up to
4.8 GHz;
\item RAM: 32 GB;
\item OS: Windows 11;
\item Compiler: gcc 16.2.0 (MSYS2), \texttt{-O3 -fopenmp}.
\end{itemize}

The thread counts tested were $p \in \{1, 2, 4, 8, 16, 22, 28\}$: $p = 22$
matches the number of hardware contexts and $p = 28$ deliberately
oversubscribes the machine. Explicit thread affinity
(\texttt{OMP\_PROC\_BIND}/\texttt{OMP\_PLACES}) could not be enforced, because
libgomp ignores it on Windows; the OS scheduler placed the workers.

\subsection{Speedup and Efficiency Definitions}
\label{sec:definitions}

The performance metrics used are:
\begin{equation}
S = \frac{T_{\text{sequential}}}{T_{\text{parallel}}}, \qquad
E = \frac{S}{p},
\end{equation}
where $S$ is the speedup, $E$ is the efficiency, and $p$ is the number of
threads. All values in Tables~\ref{tab:main}--\ref{tab:sweep} and in
Figs.~\ref{fig:speedup}--\ref{fig:efficiency} are computed from median
times.

\subsection{SIMD Vectorization Study}
\label{sec:simd}

The optional extension evaluates the sequential i-k-j kernel under three
compiler configurations, all single-threaded, plus the i-j-k \texttt{-O3}
baseline (Table~\ref{tab:simd}, Fig.~\ref{fig:simd}). Disabling
vectorization (\texttt{-fno-tree-vectorize}) isolates the effect of the loop
reorder alone: it is $2.98 \times$ faster than the i-j-k baseline at
$n = 1000$, purely from better data locality. Auto-vectorization
(\texttt{-O3}) then contributes a further $1.55 \times$, and
\texttt{-march=native} another $1.19 \times$, for a total of $5.47 \times$
over the baseline kernel. The compiler report
(\texttt{-fopt-info-vec-optimized}) confirms that the i-k-j innermost loop is
vectorized while the i-j-k innermost loop (a floating-point reduction) is
not, exactly as predicted by dependency analysis~\cite{hager2011}. The
compiler flag documentation is available in the GCC manual~\cite{gccopt}.

\section{Discussion}
\label{sec:discussion}

For matrix size $250 \times 250$, the parallel version only marginally
outperforms the sequential one at low thread counts, and its speedup curve is
noisy: the runtime is only a few milliseconds, so thread-management costs and
measurement quantization are a sizeable fraction of the total. For larger
matrices, the parallel version significantly outperforms the sequential
baseline, exactly as expected from an $O(n^3)$ workload.

The OpenMP implementation consistently achieves the best performance for
$n \geq 500$, with a practical sweet spot at $p = 8$--$16$ threads. The
maximum speedup obtained was approximately $5.45 \times$ using 22 threads,
leading to an efficiency of:
\[
\eta = \frac{5.45}{22} \approx 25\%.
\]
This behavior aligns with Amdahl's Law~\cite{amdahl1967}: since a portion of
the program is not
effectively parallelizable, the speedup eventually saturates even when
increasing threads. Here the ``serial part'' is not literal code --- the
kernel has no serial section --- but synchronization, scheduling and
memory-bandwidth contention behave like one; fitting the observed speedups
yields an effective serial-plus-overhead fraction of roughly 9--15\%. Two
machine-specific effects reinforce the saturation: the CPU is
heterogeneous~\cite{intel155h} (only 6 P-cores, so a team of 16--22 threads
necessarily includes slower E-core workers), and the working set of three
$1000 \times 1000$ matrices ($\approx$24 MB) exceeds the shared L3, so
concurrent workers compete for memory bandwidth~\cite{williams2009}. The mild
superlinearity at $p = 2$ ($S = 2.07$) is most
plausibly a turbo-frequency regime effect and is reported as observed.

A useful cross-check emerges from the SIMD study: the best parallel
configuration of the baseline i-j-k kernel ($p = 16$: 157.7 ms) and the
single-threaded vectorized i-k-j kernel with \texttt{-march=native}
(156.8 ms) are essentially tied. Each technique buys roughly the same
$5.5 \times$ on this workload, but they act on different resources (cores
vs.\ vector units), so they are complementary rather than substitutes.

The main limitations of the study are: a single machine and compiler; one
parallelization strategy (static row partitioning, no cache blocking);
matrices up to $n = 1000$ only; inability to control thread affinity on
Windows/libgomp; and measurement noise comparable to the runtime for the
smallest sizes. The conclusions are therefore limited to the configurations
actually measured.

\section{Synchronization Considerations}
\label{sec:sync}

In this project, synchronization primitives such as locks, atomics or
explicit barriers inside the kernel were not required, because each thread
computes independent rows of the resulting matrix with a static schedule: the
outer loop (rows of $\mathbf{C}$) is partitioned with
\texttt{schedule(static)}, and every row of $\mathbf{C}$ is written by
exactly one thread. Therefore, no shared write operations occur, and the
parallel result is bit-identical to the sequential one (confirmed by the
elementwise comparison, whose maximum difference is exactly zero).

If a block-based (tiled) parallelization strategy were implemented, or if
threads shared partial accumulators, synchronization mechanisms would become
necessary to avoid race conditions. The same applies to dynamic scheduling
with a shared loop counter, which typically requires an atomic increment or
a reduction.

\section{Resource Usage}
\label{sec:resources}

The parallel implementations increase memory access pressure, as multiple
threads attempt to read rows from matrix $\mathbf{A}$ and columns from matrix
$\mathbf{B}$; in the i-j-k order the innermost loop walks a column of
$\mathbf{B}$ with stride $n$, which is unfavorable for the cache
prefetcher~\cite{hager2011}. However, since each thread writes to a distinct
row of
$\mathbf{C}$, no write contention occurs.

The measured process working set is essentially constant across thread counts
($\approx$30.5 MB for $n = 1000$: the three matrices account for about
24 MB, plus the C runtime and per-thread stacks, which grow slightly with
$p$). The experiment is therefore not limited by memory capacity, but by
memory \emph{bandwidth}: the results show that performance scales until
bandwidth becomes the limiting factor, which on this machine happens around
$p = 16$. The sequential i-k-j variant reduces memory pressure by the same
amount that threading reduces compute time, because its innermost loop
updates a contiguous row of $\mathbf{C}$ from a contiguous row of
$\mathbf{B}$ --- better locality and vectorizability at once.

\section{Conclusion}
\label{sec:concl}

Parallelism allows a substantial reduction in execution time for large matrix
operations: up to $5.45 \times$ on the tested machine, with the OpenMP
implementation being the best performer among the tested configurations at
$p = 8$--$16$ threads. Thread management overhead makes parallel execution
useless for small matrices, and efficiency drops quickly beyond $p \approx 8$
as bandwidth and core heterogeneity dominate. The optional SIMD study shows
that a vectorizable loop order with \texttt{-march=native} reaches the same
$5.5 \times$ in a single thread, confirming that vectorization and threading
are complementary.

Future work could include:
\begin{itemize}
\item Combining OpenMP with the vectorized i-k-j kernel;
\item Enforcing thread affinity and repeating the study on a homogeneous
server CPU;
\item Cache blocking (tiling) to improve locality for large $n$;
\item GPU acceleration using CUDA / OpenCL libraries.
\end{itemize}
